  - 키 `hd19_saved_results`에 최근 20건까지 JSON 배열로 저장.
  - `hd19SaveResult()`/`hd19LoadResultList()` 시그니처(함수명·호출 방식)는 그대로 유지해
    `index.html`의 훅(`window.hd19OnAnalyze`)이나 버튼 `onclick`을 고칠 필요가 없었다.
  - `isTableMissing()` 등 "테이블 없음" 방어 로직은 이제 의미가 없어 전부 제거.
- `index.html`: 스크립트 태그(`lib/supabase.min.js`) 제거, "4. 결과 저장 (서버)" →

- `README.md`/`CLAUDE.md`의 Supabase 관련 서술 전부 정정(§4 데이터 스키마, §6 검증 등).

### 2. 계산 엔진 검증
- `analyze()`와 그 아래 Jacobi/Cholesky 등은 **DOM과 얽혀 있어 이식 당시(2026-08-28)
  테스트로 재현하지 않았던 부분**이다. 이번에 처음으로 독립 재구현해 검증했다.
- `test/engine.test.js` 신설 — index.html의 수식을 복붙하지 않고 별도로 다시 짜서
  대조(복붙 검증은 같은 실수를 그대로 통과시키므로 의미가 없다).
- 검증 방법: `setExample()`의 대칭 예시 데이터(4개 마운트가 X=0·Y=0 평면 대칭, 전부 Z=0)는
  물리적으로 병진-회전 커플링이 완전히 상쇄돼 6개 모드가 전부 순수하게 디커플되어야 한다.
  - Z-bounce 모드 이론값 `f = √(4·kz_total/m) / 2π = √(1,200,000/1000)/2π ≈ 5.5133 Hz`를
    직접 손으로 계산해 대조 → **소수점 6자리까지 정확히 일치**.
  - 6개 모드 전부 지배 DOF 순도 100%(완전 디커플) 확인.
  - x/y 모드 주파수가 대칭 배치로 인해 같은 값(4.2706 Hz)으로 나오는 것도 확인.
  - **검사기 자체 검증(§5.5)**: N/mm→N/m 단위변환을 일부러 빼먹은 버전을 만들어 비교했더니
    주파수가 정확히 √1000배 어긋나는 것을 확인 — 검사기가 실제로 단위 버그를 잡는다는 것을
    증명했다.
- 결론: **계산 엔진에서 버그를 찾지 못했다.** 원본 제작자(김완호 님)의 구현이 정확하다.
  `js/interpret.js`(결과 해설)도 `m.f`(Hz)·`m.vec`·`m.dominant`를 `analyze()`가 만드는
  구조 그대로 소비하고 있어 단위·인덱싱 불일치 없음을 확인.

### 3. 스모크 테스트 수정 (실제로 깨져 있던 것 발견)

  스모크 테스트가 페이지 로드 후 팝업을 닫지 않고 바로 `#saveBtn`을 클릭해 **팝업이
  클릭을 가로채 타임아웃으로 실패**하고 있었다. 팝업 닫기 단계를 추가해 수정.
